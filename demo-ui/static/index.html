Agent Delegation Consent

        
      

      
Before an AI agent can act on your behalf, you must explicitly authorize which agents may do so. This consent is stored as a Keycloak user attribute and included in your OIDC token as the may_act claim (RFC 8693 §4.4). Without consent, the delegation will be denied by OPA policy.


      

        
Current Consent

        

          
Log in first to view your agent consent settings.

          

        

      


      

        
Update Agent Consent

        

          
Select which agents you authorize to act on your behalf. The first selected agent becomes the primary (may_act.sub), and all selected agents are included in the audience (may_act.aud).

How It Works

        

          Before (hardcoded): Every user's token contained the same may_act claim, authorizing all agents for all users.

          Now (dynamic): Each user's agent_consent attribute in Keycloak controls which agents they authorize. The oidc-usermodel-attribute-mapper reads this attribute at token issuance time and emits it as the may_act claim. Changing consent requires re-authentication to get a fresh token.


          Token flow: User attribute → Keycloak mapper → may_act claim in OIDC token → OPA checks may_act.aud contains the requesting agent's SPIFFE ID → Token Exchange proceeds or denies.

Token Exchange (RFC 8693)

        
      

      
Two tokens go in (human OIDC + agent SPIFFE), one delegation token comes out. This is the core of the identity broker — the Token Exchange Service validates both tokens, checks policy, and mints a delegation token with a nested act{} claim.

Vault Credential Brokering

        
      

      
The agent presents the delegation token from Step 5 to the Token Exchange Service. Token Exchange validates the token (RS256 signature, expiry, revocation status), extracts the authorized scope, and uses its own Vault credentials to broker dynamic database credentials. The agent never authenticates to Vault directly — the delegation token IS the proof of human authorization that gates credential access.

Broker Credentials via Delegation Token

        

          
The agent makes a single call to Token Exchange, presenting the delegation token as proof of human authorization. Token Exchange validates the token, maps the scope to a Vault role, and uses its own privileged Vault token to broker dynamic database credentials. The agent never touches Vault directly.

Phase 1 of 7

Alice Logs In

The agent never sees her password. She authenticates directly with the identity provider using the Device Authorization Flow.
Alice opens her chat interface and types: "Show me high-value orders from the last month." The AI agent needs to query a database to answer this — but first, it needs Alice to prove who she is and consent to the agent acting on her behalf.
Alice's terminal
HUMAN AUTHORIZATION REQUIRED Open this URL in your browser: https://login.acme.com/device?code=ABCD-EFGH Enter code: ABCD-EFGH (The agent does NOT have your password)
Alice opens that link on her own machine — her own browser, her own password manager, her own MFA authenticator. She logs in, sees a consent screen, and clicks "Approve." The agent never touches her credentials. It just waits.
OAuth 2.0 Device Authorization Grant (RFC 8628) — the same flow your smart TV uses when it asks you to visit a URL and enter a code. The agent receives a scoped, time-limited access token — never a password.

Two key claims:
groups — Alice belongs to data-analysts and trading-team. These determine what she can delegate.
may_act — Set by her administrator, explicitly saying "this user is authorized to delegate to an AI agent." Without it, the entire flow stops here.
Phase 2 of 7

Agent Proves Its Identity

The agent can't just say "trust me." It needs a cryptographic identity tied to its actual workload — that's what SPIFFE provides.
Alice has proven who she is. Now the agent needs to prove who it is. In a world of containers and microservices, a software process needs a cryptographic identity — verifiable by anyone, tied to the specific workload running on a specific machine.
SPIFFE (Secure Production Identity Framework for Everyone) is a passport system for software: every workload gets a globally unique identity (a SPIFFE ID) and a short-lived, signed certificate (a SVID) that proves it.

Phase 3 of 7

The Delegation Exchange

The agent bundles Alice's token and its own SPIFFE identity, then requests delegated access via RFC 8693 Token Exchange.
The agent now has two things: Alice's OIDC token (proving a human authorized this) and its own SPIFFE identity (proving which agent is performing it). It sends both to the Token Exchange Service.
RFC 8693 Token Exchange Request ▼
"grant_type": "urn:ietf:params:oauth:grant-type:token-exchange", "subject_token": "<Alice's OIDC JWT>", // who authorized "subject_token_type": "urn:ietf:params:oauth:token-type:access_token", "actor_token": "<Agent's SPIFFE JWT-SVID>", // who is acting "actor_token_type": "urn:ietf:params:oauth:token-type:jwt", "scope": "readonly", // what access "audience": "database" // target resource
In plain English: "I am agent query-agent, acting on behalf of Alice, and I need readonly access to the database."

This token is the receipt for the delegation. Anyone who inspects it can answer: who authorized this? (Alice), who is acting? (query-agent), what can they do? (readonly), when does it expire?

Phase 5 of 7

Sub-Agent Delegation

The chain extends: the query agent delegates to a specialized SQL executor via another RFC 8693 exchange. Scope can only narrow, never widen.
Sometimes an agent needs help. The query agent delegates SQL execution to a sub-agent — a purpose-built agent that only knows how to run SQL. It doesn't hand the sub-agent Alice's original token. Instead, it performs another RFC 8693 token exchange, using its own delegation token as the subject_token.

OPA checks: depth < max (3), scope must be equal or narrower
How policy prevents abuse:
1. Scope Narrowing — A sub-agent can never gain more access than its parent. The scope hierarchy is explicit:
readwrite ──> readonly ──> db:read │ db:query └──────> db:write ──> db:read An arrow means "implies." Having readwrite implies readonly. But db:read never implies readwrite — you can't escalate upward.
2. Chain Depth Limit — Maximum delegation depth is configurable (default: 3).
Human → Agent = depth 0.   Agent → Sub-Agent = depth 1.   Prevents infinite delegation chains.
Nested act Claim Sub-agent's delegation token — full chain embedded ▼
{ "sub": "alice@acme.com", "act": { "sub": "spiffe://demo.local/subagent/sql-executor", "act": { "sub": "spiffe://demo.local/agent/query-agent", "act": { "sub": "alice@acme.com" } } } } // Read from the inside out: // Alice authorized query-agent, // which delegated to sql-executor, // which is now acting as Alice. // The complete chain of trust is in the token itself.
Phase 6 of 7

The Credentials Disappear

Five minutes after issuance, Vault automatically revokes the database credentials. No manual rotation, no cleanup, no forgotten keys.
Five minutes after issuance, Vault automatically revokes the database credentials:
DROP ROLE IF EXISTS "v-token-readonly-3ee8b521";
Any attempt to connect with those credentials fails:
Connection attempt after expiry
FATAL: role "v-token-readonly-3ee8b521" does not exist Connection refused. Credentials ceased to exist.
If the agent (or anyone who intercepted the credentials) tries to use them after expiry, they get nothing. There's no password to rotate, no key to revoke manually, no "forgot to clean up" scenario. The credentials simply cease to exist.

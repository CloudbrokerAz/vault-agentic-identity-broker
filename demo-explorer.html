Phase 1: Human Authentication

The human proves their identity via Keycloak OIDC — the agent never sees the password

Alice asks her AI agent: "Show me all orders over $1,000 from last month." Before the agent touches the database, Alice must prove who she is and consent to the agent acting on her behalf. This uses the OAuth 2.0 Device Authorization Grant (RFC 8628) — the same flow smart TVs use.
▷ Device Authorization Flow
1Agent → KeycloakPOST /auth/device {client_id: "demo-cli"}
2Keycloak → Agentdevice_code + user_code: "ABCD-EFGH"
3Agent displays URL + code to human💻 "Open this URL and enter code ABCD-EFGH"
4Human → KeycloakOpens browser, logs in with password + MFA, clicks "Approve"
5Agent → KeycloakPolls: POST /token {grant_type: device_code} (every 5s)
6Keycloak → Agentaccess_token (JWT) — agent never saw the password
🔐
Key security property: The agent never touches the human's credentials. The human authenticates directly with Keycloak in their own browser. The agent just polls until it receives a scoped, time-limited token.
🔍 JWT Access Token (decoded)
Two critical claims to notice:
• groups — determines what scopes the human can delegate (e.g., data-analysts can delegate readonly).
• may_act — explicitly authorizes delegation to AI agents. Without it, the entire flow stops.
🛡

Phase 2: Agent Identity (SPIFFE/SPIRE)

The agent proves its own identity via cryptographic workload attestation

The human has proven who they are. Now the agent must prove who it is. A software process can't just claim "I'm the query agent — trust me." It needs a cryptographic identity tied to the specific workload running on a specific machine. This is what SPIFFE (Secure Production Identity Framework for Everyone) provides.
▷ SPIRE Workload Attestation
1Agent → SPIRE AgentFetchJWTSVID via Unix domain socket
2SPIRE Agent attests the workloadChecks process UID, container labels, registration entries
3SPIRE Agent → SPIRE ServerRequest JWT-SVID signing for matched SPIFFE ID
4SPIRE Server → SPIRE AgentSigned JWT-SVID (1-hour TTL, auto-rotated)
5SPIRE Agent → AgentJWT-SVID returned — cryptographic proof of workload identity
🛡 Agent SPIFFE Identity
🔒
Why SPIFFE? Unlike API keys or shared secrets, a SPIFFE SVID is:
• Cryptographically signed by the SPIRE CA
• Short-lived — auto-rotates, can't be stockpiled
• Attested — tied to the actual running workload, not just a name
• Verifiable by anyone who trusts the demo.local trust domain

Phase 3: RFC 8693 Token Exchange

The agent bundles both identities and requests delegated access

The agent now has two things: the human's OIDC token (proving who authorized this) and its own SPIFFE identity (proving which agent is acting). It sends both to the Token Exchange Service following RFC 8693 (OAuth 2.0 Token Exchange).
📤 RFC 8693 Token Exchange Request
▷ Token Exchange Orchestration
1Agent → Token ExchangePOST /v1/token/exchange {subject_token, actor_token, scope}
2Token Exchange → KeycloakValidate subject_token via userinfo endpoint
3Token Exchange validates actor_tokenSPIFFE trust domain check + registered agent lookup
4Token Exchange → OPAPOST /v1/data/delegation {human, agent, scope} → policy evaluation
5OPA → Token ExchangeDecision: ...
6Token Exchange → VaultGET /v1/database/creds/ai-agent-{scope}
7Token Exchange → AgentDelegation token + DB credentials

Phase 5: Vault Dynamic Credentials

Vault creates a unique PostgreSQL user with time-limited, scoped permissions

⛔
This step is skipped. OPA denied the delegation request, so no credentials are issued. Change the scenario controls to see a successful flow.
With policy approval, Vault doesn't hand out a shared password. Instead, it creates a brand new PostgreSQL role specifically for this session — unique per delegation, auto-expires in 5 minutes.

What this achieves:
• Unique per session — every delegation gets its own database user
• Scoped — readonly role can only SELECT, never INSERT/UPDATE/DELETE
• Time-limited — role expires in 5 minutes, even if nobody revokes it
• Traceable — any query from this user can be correlated back to Alice's delegation

Phase 7: Audit Trail & Credential Revocation

7-layer correlated audit trail + automatic credential lifecycle management

After the interaction, every layer has logged what happened — independently, with correlated identifiers. An auditor can start at any layer and trace the full chain. The session ID and Vault-generated username serve as correlation keys across all systems.

Sub-Agent Delegation Chains

Agents can delegate to specialized sub-agents — scope can only narrow, never widen

Sometimes an agent needs help. The query agent might delegate SQL execution to a specialized sub-agent. This uses another RFC 8693 exchange, with the parent's delegation token as the subject_token. Two critical rules prevent abuse: scope narrowing (sub-agents can't gain more access than their parent) and chain depth limits (default max: 3).
🔗 Delegation Chain Extension
HUMAN (Subject)
alice@acme.com
groups: data-analysts, trading-team
↓ OIDC Token (may_act)
AGENT (Depth 0)
spiffe://demo.local/agent/query-agent
scope: readonly
↓ RFC 8693 (delegation token as subject)
SUB-AGENT (Depth 1)
spiffe://demo.local/subagent/sql-executor
scope: readonly narrowed or same
↓ Query with own Vault credentials
DATABASE
PostgreSQL (appdb)
🔗 Nested act{} Claim (full chain in the token)
⛔ Chain Depth Limits
Depth 0: Human → Agent allowed
Depth 1: Agent → Sub-Agent allowed
Depth 2: Sub-Agent → Sub-Sub allowed
Depth 3+: DENIED — max_delegation_depth_exceeded
🔙 Scope Narrowing Rules
readwrite → readonly allowed (narrowing)
readonly → readonly allowed (same)
readonly → db:read allowed (narrowing)
readonly → readwrite DENIED — scope_narrowing_violation
db:read → readwrite DENIED — scope_narrowing_violation
⚠
Key principle: Each level in the delegation chain can only narrow permissions, never widen them. This ensures that no matter how many levels of delegation occur, the sub-agent can never gain more access than the original human authorized.
